# Матрица приёмки редизайна Nexora

Матрица сохраняет 23 исходных критерия аудита. Проверять на отдельном Compose с PostgreSQL и RabbitMQ. Первый набор данных — успешный профиль CRM, отказ ERP при успешном Billing, повтор после восстановления, дубликат и устаревшее событие, платёж Billing → CRM, отклонение входного контракта. Использовать реальные переходы backend.

| ID | Готово, когда | Как проверить |
| --- | --- | --- |
| AC-01 | Из результата CRM можно открыть событие за одно действие. В деталях видны источник, Event ID, Correlation ID, тип и цели. Из Billing payment всего одна цель CRM. | Два браузерных прогона. Сравнить цели и идентификаторы с `GET /api/messages/:id`. |
| AC-02 | При ERP RETRY/DEAD и Billing SUCCEEDED оба состояния видны рядом в первом содержательном экране или в первой мобильной группе. Общий результат явно смешанный. | Переключить ERP в режим отказа, дождаться RETRY, затем DEAD. Сверить тексты и иконки. |
| AC-03 | Транспортный успех и бизнес-эффект имеют отдельные подписи для APPLIED/SAME/STALE. Показатель ошибок разделяет входные события и доставки. | Повторить публикацию версии 1 после версии 2. Сверить версии проекций. |
| AC-04 | Целевая доставка показывает четыре завершившиеся попытки при лабораторном отказе, время с зоной, серию, HTTP при наличии, класс ошибки и ETA только в RETRY. | Сравнить список и время с `attempts` и `next_at`. |
| AC-05 | INVALID_CONTRACT представлен как карантин входного события без получателей и без кнопки повторной доставки. Указано, что исходное тело недоступно. | Отправить учебный неверный контракт, открыть карточку из DLQ. |
| AC-06 | По точному Event ID и Correlation ID находятся ожидаемые записи. Ручной возврат и Back сохраняют применённое состояние, включая сортировку при её наличии и номер страницы. | E2E на двух идентификаторах, раскрытии строки, возврате и перезагрузке с новым входом. |
| AC-07 | Некорректный UUID объяснён у поля до запроса. Корректный ID без результатов и сетевой сбой показаны разными состояниями. | Ввести `invalid-id`, новый UUID и отдельно отключить API в тесте только локальным условием сети. Проверить сохранение формы. |
| AC-08 | Из строки DLQ/Ошибок открывается точная доставка или карантинное событие. Есть копирование полного Event, Correlation и Delivery ID с обратной связью. | Две ошибки для разных целей на одном событии. Каждая ссылка открывает правильную цель. Сверить буфер обмена. |
| AC-09 | Replay показывает принятие запроса и отдельно итог. Успех сохраняет 4 старых попытки и добавляет новую серию той же Delivery ID. Другие цели остаются без новых попыток. | Восстановить ERP, нажать replay один раз, сверить поколения и ID. Проверить ссылку на историю после выхода из активного DLQ. |
| AC-10 | Публикация дубликата по тому же Event ID явно отличается от создания нового события. Утверждение о дедупликации имеет доказательство или помечается как результат отдельной проверки. | Сравнить доставку и попытки до/после, проверить результат публикации. |
| AC-11 | Сверка различает недоступный сервис, отсутствие проекции, отстающую версию и расхождение значения. Отправка восстановления ведёт к новому событию и повторной сверке. | Подготовить синтетические расхождения, сверить с `issues`. Проверить сохранение UUID и результата. |
| AC-12 | При Tab пользователь может пропустить навигацию, открыть журнал, найти запись, раскрыть попытки и вернуться. После закрытия меню/диалога фокус возвращается к вызвавшей кнопке. | Ручной проход в Chromium и Safari либо Firefox, с записью последовательности и видимого контура. |
| AC-13 | Контролы имеют доступные имена, нормальный текст ≥4,5:1, необходимые контуры/индикаторы ≥3:1, размер цели ≥24×24 CSS px или применимое исключение. Изменение статуса доступно без цвета и не перемещает фокус. | Ручные замеры, дерево доступности, выборочная автоматизация, проверка VoiceOver/NVDA для основного пути. |

Сложная таблица или Raw Data прокручиваются внутри подписанной области. | Проверить `scrollWidth <= innerWidth`, узкие скриншоты и клавиатуру в области прокрутки. |
| AC-15 | Мобильное меню в закрытом состоянии занимает максимум 112 px вертикального пространства вместе с идентификацией продукта. Скрытые ссылки не попадают в Tab. Действия можно вызвать без hover. | Измерить на 390 и 320 px, проверить Escape и клавиатурное открытие. |
| AC-16 | Lab доступна только admin из изолированного окружения. Стенд явно обозначен. Пароль или ключ не попадает в снимки, clipboard диагностик и payload. | Viewer и operator получают отказ от API. Admin на стенде без LAB_MODE не видит раздела и получает отказ. |
| AC-17 | Из маршрута можно открыть контракт и конкретную операцию. Для CRM→ERP объяснены SOAP 1.1 и маппинг; для Billing→CRM показана REST-проекция оплаты. Все 6 файлов доступны. | Сверить ссылку, метод, XML/JSON поля и HTTP 200 файлов с версиями в репозитории. |
| AC-18 | Миграции, права, маршруты, дедупликация, повторные доставки и прежние глубокие ссылки проходят регрессии. Изменение UI не запускает мутаций на просмотре. | `scripts/run-integration`, тесты проекта и E2E с контролем POST/PUT. |
| AC-19 | Архитектура и выбранное сообщение имеют отдельные представления. Направления и протоколы подтверждены текущим контрактом. Для каждого узла доступна равнозначная текстовая информация. | Сравнить оба представления с архитектурой и API для CRM и Billing. Проверить Tab и чтение без графики. |
| AC-20 | Каждая метрика имеет понятную популяцию и доступный переход к данным, если API позволяет фильтрацию. Показатели без времени наблюдения не изображают историю. | Сравнить число с API, проверить период, единицу и ссылку. При недоступности брокера показать «Данные недоступны». |
| AC-21 | В фоне обновляются только активные рабочие представления. В режиме reduced motion интерфейс остаётся статичным, новые состояния не скрыты анимацией. | AC-22 | При потере ответа на изменение оплаты UI показывает «Результат операции пока неизвестен» и путь к проверке результата. Автоматического повторного POST нет. Если вводится ключ команды, два запроса с тем же ключом дают одно исходное событие. | На отдельной базе прервать ответ после подтверждённой записи, проверить видимое сообщение, число запросов и число событий до и после. |
| AC-23 | Переход из подтверждённой записи источника к временно ещё отсутствующему Event ID показывает ожидание приёма и сохраняет ID. Неизвестная глубокая ссылка по-прежнему получает понятное состояние 404. | Открыть подтверждённую ссылку до Inbox и дождаться деталей. Проверить отдельно случайный UUID и отказ API. |

## Методика

До редизайна тест создания профиля проверял два массива статусов в течение пяти секунд. На чистом стенде первый получатель успел завершить обработку, второй остался PENDING в момент проверки. Редизайн проверяет точный Event ID и состояние каждой цели в интервале с конечной границей. Сценарии создают собственные профили и сравнивают результат с API. ERP после сценария возвращается в доступное состояние, включая ошибку подтверждения команды изменения доступности.

Проверка потери ответа отправляет оплату на настоящий Billing. Playwright ждёт ответа 201, затем подменяет только подтверждение, получаемое браузером, на 502. Сценарий сверяет событие и проекцию CRM, а также проверяет, что ровно одна команда была отправлена.

Контраст вычислен для основных пар CSS-токенов. Текст на белом и на фоне страницы имеет 6,42:1 и 14,15:1 в типовых состояниях, текст статусов 7,16:1–7,38:1, контур фокуса на фоновом поле 5,65:1, граница контролов на белом 4,24:1. Это выборочная проверка цветовых пар. Проверка клавиатуры и вспомогательных технологий выделена отдельными критериями.

### Запуски

- Исходная версия, отдельный стенд, Chromium — 2 из 3. Положительный сценарий остановился на ожидании второй доставки.
- Первый стенд разработки столкнулся с завершением API по OOM. На втором стенде ранние проверки застали запуск CRM и Worker. Эти прогоны показали 1 из 6 и 1 из 7. Следующий предварительный прогон остановил тесты на проверке готовности после сбоя ERP. После восстановления доступности ручной сценарий завершился успешно.
- [Первый полный CI редизайна](https://github.com/bivaettttt/nexora/actions/runs/43745589954) — 8 pytest, 7 Playwright, REST/SOAP smoke, сценарии интеграции и восстановления, линтинг, спецификации, сборка.
- После запуска всех сервисов локальный прогон дал 5 из 7. В одном случае CRM вернула 502, в другом чтение списка, начатое до подтверждённой записи, скрыло новый профиль. Список теперь сразу учитывает подтверждённую запись и затем перечитывается. Два целевых повтора прошли, включая оплату с потерянным подтверждением. В тест добавлена задержка первого чтения списка.
- Локальное подтверждение MCP. Event ID **ad62be2d-753e-4daa-bca0-0b672accd675**, Correlation ID **a90c0333-9952-5157-ab9a-e243b000ab92**, Delivery ID ERP **24fb73f0-db1a-4776-8705-f0d5fd48a82f**. Подтверждён переход из DLQ к исходной доставке, повтор и отдельный итог восстановления.

Для повторной записи снимков укажите абсолютный каталог в NEXORA_SCREENSHOTS при запуске Playwright. Галерея содержит 17 снимков Chromium с изолированного стенда CI. В тесте HTTP 502 изменено только подтверждение, получаемое браузером.
