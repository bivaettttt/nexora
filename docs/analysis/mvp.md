# Nexora · Спецификация MVP / MVP specification

CRM ведёт профиль клиента, ERP — контрагента, Billing — договор и факт оплаты. Nexora связывает их и позволяет оператору расследовать расхождения. Граница MVP — четыре независимых приложения с синтетическими данными, локальная сеть Compose и контракт v1. Внешние корпоративные подключения, реальные платежи и глобальная exactly-once доставка вне объёма.

The MVP connects synthetic CRM, ERP and Billing systems through versioned contracts. Operators can diagnose and recover individual deliveries. Production connectivity and real payments are outside scope.

## Участники и истории / Stakeholders and stories

| ID | Участник и потребность / Need | Критерий / Acceptance |
|---|---|---|
| FR-01 | Сотрудник CRM создаёт и обновляет профиль / Publish a profile | Запись и событие фиксируются вместе, ERP и Billing получают свою проекцию |
| FR-02 | Сотрудник Billing фиксирует оплату / Record payment | CRM принимает статус, ERP отсутствует среди получателей |
| FR-03 | Оператор оценивает ход обмена / Trace exchange | По event/correlation ID видны payload, версия, доставки и попытки |
| FR-04 | Оператор устраняет временный отказ / Recover transient errors | Ошибка ERP не задерживает результат Billing, число повторов ограничено |
| FR-05 | Оператор разбирает DLQ / Investigate quarantine | Неверный контракт изолируется, доставка повторяется после исправления причины, история сохраняется |
| FR-06 | Владелец данных защищает актуальность / Preserve freshness | Повтор и запоздалая версия не изменяют уже применённую более новую проекцию |

| FR-08 | Администратор запускает эксперимент / Run isolated failure cases | Фиксированные сценарии показывают реальные результаты RabbitMQ, API и БД |
| FR-09 | Наблюдатель проверяет контракты / Inspect interfaces | Реестр и интерфейс показывают маршруты, маппинг, ошибки и ссылки на контракты |

## Словарь / Glossary

- **Профиль / profile** — версия данных CRM с полями legal name и contact email.
- **Глобальный ID / global ID** — UUID клиента, общий для всех систем. У каждой системы отдельный local ID.
- **Платёжный статус / payment status** — состояние учебного договора Billing, отдельная версия.
- **Outbox / Inbox** — транзакционный буфер источника и журнал уникальных принятых событий.
- **Delivery** — обработка одного события одним получателем. **Attempt** — отдельный сетевой вызов.
- **DLQ** — долговечный реестр изолированных событий и исчерпанных доставок.
- **Correlation ID** — UUID для связанных событий и сетевых вызовов.

## Use cases

1. **UC-01 Профиль.** CRM сохраняет профиль с версией и Outbox. Worker принимает событие, создаёт независимые доставки ERP SOAP и Billing REST. При обновлении передаётся полный снимок полей CRM. Получатели сравнивают версию.
2. **UC-02 Оплата.** Billing меняет статус существующего договора и добавляет событие. Worker отправляет в CRM. CRM меняет только поля оплаты и не публикует событие в ответ.
3. **UC-03 Восстановление.** Временный отказ ведёт к повтору с backoff. По исчерпании попыток оператор может открыть новую серию. Для непригодного входного контракта анализ сохраняется в DLQ, исправленный источник выпускает новое событие.
4. **UC-04 Сверка.** Оператор запрашивает известный UUID. Nexora читает источники через API, показывает различия. Восстановление повторно публикует актуальный CRM-профиль с новым ID события, а получатели проверяют его версию.
5. **UC-05 Лаборатория.** Администратор запускает фиксированные опыты на отдельных экземплярах приложений и очереди, затем отслеживает результаты по идентификаторам.

## Бизнес-правила / Business rules

| ID | Правило |
|---|---|
| BR-01 | CRM владеет legal name, contact email и profile version. ERP получает legal name, Billing получает legal name и email |
| BR-02 | Billing владеет payment status и payment version. ERP не принимает оплату |
| BR-03 | Новая версия заменяет проекцию. Устаревшая версия игнорируется. Та же версия с теми же данными идемпотентна |
| BR-04 | При сверке восстановление выполняется только по авторитетному источнику и не откатывает более свежую версию |
| BR-05 | Один event ID связывается с неизменяемым содержимым. Повторная доставка не создаёт новых целевых бизнес-записей |
| BR-06 | CRM → ERP/Billing и Billing → CRM. Рабочие входные сообщения не управляют адресами доставки |
