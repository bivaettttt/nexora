# Nexora Message Trace Workbench

## Исходные проблемы и рабочий сценарий

В аудите рассмотрены 62 снимка, работающая консоль и REST/SOAP-контракты. Основные проблемы проявлялись при отказе одной из двух целей, диагностике из DLQ, возврате к отфильтрованному журналу и потере ответа после команды оплаты. На телефоне навигация и широкие строки оттесняли данные.

Аналитик или инженер поддержки находит событие по Correlation ID, сверяет источник и получателей, выбирает доставку, читает попытки и контракт, при необходимости переходит к сверке или восстановлению.

| Область | Что изменилось |
| --- | --- |
| Сводка | Текущие отказы, очередь RabbitMQ и последние события. Входной карантин учитывается отдельно от ошибок доставки. |
| Журнал | Поиск по четырём идентификаторам, фильтры источника, получателя, типа, состояния и времени. Сортировка, страница и фильтры сохраняются в URL. Событие и его цели открываются отдельными ссылками. |
| Workbench | Источник, идентификаторы и время приёма. Независимые получатели, выбранная доставка, хронология, бизнес-эффект, анализ ошибки и просмотр данных. |
| Ошибки и DLQ | Ссылки ведут в конкретную доставку или входной карантин. После восстановления история доступна по тому же Delivery ID. |
| Маршруты, маппинг и контракты | Статическая архитектура показывает CRM и Billing как возможные источники, RabbitMQ и Worker как этапы обмена и REST либо SOAP как протокол получателя. Фактические назначения конкретного события видны в Workbench. |
| CRM, оплата и сверка | Подтверждённая публикация даёт ссылку на Event ID. При потере подтверждения оплаты доступны журнал по клиенту и сверка. |
| Лаборатория | Изолированные эксперименты используют исходные полномочия и синтетические данные. |

## Визуальная система и доступность

Inter используется для интерфейса, IBM Plex Mono для идентификаторов, времён и кодов. Светлая палитра сочетается с тёмно-синей шапкой и бирюзовым акцентом. Ошибка, ожидание и подтверждение обозначаются текстом и цветом. Полные значения доступны при переносе или копировании.

Мобильная шапка содержит кнопку «Разделы». Журнал и доставки переходят в адаптивные строки. Метаданные и ID переносятся. Широкие технические таблицы и payload прокручиваются внутри подписанных областей. Для навигации предусмотрены пропуск меню, видимый фокус, Escape, возврат фокуса и статические сигналы при reduced motion. Объём проверки доступности описан в матрице приёмки.

## Семантика доставки и восстановления

Транспортное состояние SUCCEEDED фиксирует завершение доставки. APPLIED, SAME и STALE описывают бизнес-эффект. При RETRY показываются причина и плановое время попытки. При DEAD доступны все попытки и подтверждение восстановления для уполномоченной роли. Принятие replay с HTTP 202 предшествует отдельному подтверждению результата. Та же Delivery ID сохраняет старые и новые попытки. Хронология использует UTC. Для входного INVALID_CONTRACT получателей нет. Доступны сохранённые диагностические метаданные.

## Неопределённый результат команды

При HTTP 502, другой серверной ошибке или потере ответа оплата может уже находиться в Billing. Интерфейс отмечает результат как неизвестный и приостанавливает повтор для клиента в текущей вкладке. Оператор проверяет события Billing и проекции по ID клиента, затем завершает проверку вручную. Для серверной идемпотентности нужна отдельная задача на контракт команды. В ней следует согласовать область и срок действия ключа, проверку запроса с тем же ключом, привязку к результату и поиск результата по ключу. Для подтверждённой публикации интерфейс ожидает регистрации в журнале до 30 секунд. Произвольная ссылка на отсутствующее событие получает состояние недоступности.

## Контракты и ограничения

GET /api/messages по умолчанию сохраняет прежние поля. customer_id, delivery_id, order и include_deliveries добавляют опциональные возможности чтения. При запросе сводки снимок данных страницы согласован на уровне PostgreSQL. Детали включают отметки replay из существующих действий. Версии контрактов, маршрутизация, миграции, права и политика доставки сохранены.

Панель показывает сохранённый JSON и рассчитанный маппинг. SOAP Envelope реконструируется по контракту. Перехват исходного HTTP-трафика, полные ответы целей и тела сообщений входного карантина отсутствуют. Агрегаты сводки ограничены текущими API. Гарантия транспорта остаётся at-least-once.
