# Nexora · Кейс для портфолио

| Раздел | Описание |
|---|---|
| Бизнес-проблема | Независимые корпоративные приложения по-разному описывают клиента. Сбои, повторы и задержки приводят к расхождениям. |
| Цель | Проследить профиль и оплату от источника до проекций, диагностировать и восстановить отказавшую доставку. |
| Моя роль | Я поставил задачу для учебного кейса, определил бизнес-сценарии и критерии приёмки. Проектирование, реализация и проверка выполнены с использованием Codex. |
| Аналитические задачи | Описать границы, участников, маппинг, владение полями, таблицу ошибок и трассируемость требований. |
| Системные требования | Независимые доставки, at-least-once, версионный контроль и наблюдаемость по correlation ID. |
| Интеграционные контракты | REST/OpenAPI CRM и Billing, SOAP/WSDL/XSD ERP, AMQP/AsyncAPI событий. |
| Архитектура | Отдельные процессы и PostgreSQL-базы, RabbitMQ, Nexora API и Worker, React-консоль. |
| Модель данных | Глобальный UUID, локальные идентификаторы, независимые версии профиля и оплаты, Outbox, Inbox, доставка и попытка. |
| Технические решения | Publisher confirm до фиксации публикации, ack после Inbox, проверка версии у получателя, отдельный поток каждой цели. |
| Обработка ошибок | Классификация отказов, ограниченный backoff с jitter, карантин и контролируемый повтор с историей. |
| Тестирование | Сетевые контракты, PostgreSQL и RabbitMQ, восстановление после отказов, Playwright, GitHub Actions. |
| Результаты | Проверены частичный успех, очередь ошибок, повтор, защита от устаревшей версии и восстановление проекции. |
| Ограничения | Синтетические данные и локальная среда. Сверка по одному клиенту, локальные ролевые ключи. |
| Демонстрация | Создать клиента → открыть событие и два маппинга → отключить ERP → увидеть успешный Billing и DLQ ERP → восстановить доставку → сверить записи. |
| Код и документация | [Репозиторий](https://github.com/bivaettttt/nexora), [требования](analysis/mvp.md), [архитектура](architecture/design.md), [проверки](testing/results.md). |
